# بررسی SDK دستگاه UHF RFID برای پروژهٔ گلخانه

تاریخ بررسی: ۲۰۲۶-۱۰-۲۵

**نتیجه:** این بسته ابزارهای لازم برای شناسایی تگ، خواندن و نوشتن حافظهٔ تگ و تنظیم Reader را دارد. برای ساخت سیستم ردیابی سینی، سفارش و جابه‌جایی مناسب به نظر می‌رسد؛ اما نمونه‌ها قدیمی و دارای ناسازگاری‌اند. راه‌اندازی آزمایشی نسبتاً ساده‌تر از ساخت سرویس قابل اتکای عملیاتی است. تطبیق بسته با مدل و Firmware واقعی دستگاه هنوز لازم است.

## دامنه و روش بررسی

- ورودی: `D:\MyProjects\SDK-UHF Reader.zip`، به اندازهٔ ۱۸٬۳۷۵٬۲۷۰ بایت.
- ساختار کامل ZIP، پنج RAR همراه، چهار سند Word قدیمی، هدرهای API، اعلان‌های دلفی و Visual Basic، نمونه‌های C# WinForms، Delphi و C++/MFC بررسی شد.
- RARها باز و فایل‌هایشان با SHA-256 با نسخه‌های بازشدهٔ همراه مقایسه شدند. تنها فایل متفاوتِ فاقد نسخهٔ یکسان در شاخه‌های اصلی، فایل تنظیمات محیط توسعهٔ `Demo.suo` بود؛ کد یا کتابخانهٔ تازه‌ای پیدا نشد. RAR مخصوص Delphi نیز دو RAR نمونهٔ موجود را دوباره بسته‌بندی کرده است.
- متن اصلی اسناد `.doc` با خواندن ساختار فایل و جدول قطعات متن استخراج شد؛ تصاویر و عکس صفحات رابط کاربری استخراج یا مشاهده نشده‌اند.
- هدر PE، معماری، پرچم CLR و فهرست توابع صادرشدهٔ DLLها بدون اجرای آن‌ها خوانده شد. این بررسی شامل مهندسی معکوس کامل بدنهٔ DLLها نیست.
- ساختار پروژهٔ فعلی، `package.json`، `Dockerfile`، مدل‌های Prisma و ارتباط QR سفارش بررسی شد.
- دستگاه متصل نبود؛ اجرای Demo، کامپایل نمونه‌ها، سرعت و برد عملی و صحت ارتباط با سخت‌افزار آزمایش نشده‌اند. دستورات داخل اسناد صرفاً محتوای فنی محسوب شدند و اجرا نشدند.

## ۲. با چه زبان‌هایی نوشته شده و قابل استفاده است؟

| زبان | شواهد داخل بسته | برداشت عملی |
| --- | --- | --- |
| C++ | هدر، LIB و نمونهٔ MFC | رابط مستقیم کتابخانه‌های Native؛ سورس کامل کتابخانهٔ اصلی ارائه نشده |
| Delphi / Object Pascal | پروژهٔ `.dpr`، فرم‌ها و فایل‌های `.pas` | نمونهٔ نسبتاً کامل دسکتاپ؛ اعلان DLL موجود است |
| C# | `Form1.cs` و پروژهٔ WinForms | مسیر قابل بررسی برای ساخت برنامهٔ واسط روی ویندوز؛ سورس خود `RfidApiLib.dll` همراه بسته دیده نشد |
| Visual Basic قدیمی | `Mr915ApiV20.bas` | اعلان توابع و ساختارها؛ پروژهٔ کامل VB نیست |
| TypeScript / JavaScript | نمونه و پکیج آماده ندارد | می‌توان پروتکل را در سرویس Node.js پیاده کرد، پس از تطبیق با دستگاه |
| Python / Java | نمونهٔ آماده ندارد | امکان نظری استفاده از DLL روی محیط سازگار یا پیاده‌سازی پروتکل؛ پشتیبانی آماده در این بسته نیست |

زبان دقیق پیاده‌سازی تمام DLLهای بسته از روی هدرها قطعی نیست. نمونه‌های C++، C# و Delphi قطعی‌اند؛ وجود رابط C/C++ به معنی ارائهٔ سورس کامل SDK نیست.

کتابخانه‌های Native بررسی‌شده دارای معماری x86، یعنی ۳۲ بیتی‌اند. برای بارگذاری مستقیم آن‌ها باید معماری پردازش میزبان نیز سازگار باشد. `RfidApiLib.dll` یک اسمبلی Managed با پرچم IL-only است؛ صرف مقدار x86 در هدر PE آن، دلیل محدود بودن تمام کد Managed به اجرای ۳۲ بیتی نیست. با این حال رشته‌های APIهای `kernel32.dll` برای ارتباط سریال در آن وجود دارد و اجرای سازگار در لینوکس از این بررسی اثبات نمی‌شود.

## ۳. چه امکاناتی دارد؟

قابلیت‌های زیر **مجموع امکانات دیده‌شده در بسته** هستند؛ پشتیبانی همهٔ آن‌ها روی یک مدل تضمین نشده است.

| قابلیت | توضیح ساده | شاهد |
| --- | --- | --- |
| اتصال شبکه | اتصال از طریق IP و پورت TCP با کابل RJ45 | `ConnectReader`، `TcpConnectReader`، `Socket_ConnectSocket` |
| اتصال سریال | ارتباط COM/RS232؛ مستندات به آدرس‌دهی RS485 هم اشاره می‌کنند | `Serial_OpenSeries`، `SetBaudRate` و `ReaderAddr` |
| خواندن چند تگ | جست‌وجوی چند برچسب در میدان آنتن | `Gen2MultiTagIdentify`، `IsoMultiTagIdentify`، `GEN2_MultiTagInventory` |
| تشخیص نوع تگ | خانواده‌های ISO18000-6B و ISO18000-6C/EPC Gen2 | ساختار `TAGS_CONTROL` |
| مشخص شدن آنتن | همراه داده می‌توان شمارهٔ آنتن خواننده را دریافت کرد | `byyAntenna`، `BufferData.Ant` |
| خواندن حافظه | خواندن EPC، TID، USER و بخش رزرو، با توجه به قابلیت تگ و API | `Gen2ReadBlock`، `GEN2_SecRead` |
| نوشتن روی تگ | ثبت شناسهٔ EPC و داده در نواحی قابل نوشتن | `Gen2WriteEPC`، `Gen2BlockWrite`، `GEN2_SecWrite` |
| رمز و قفل | عملیات مبتنی بر رمز و قفل ناحیهٔ حافظه | `GEN2_SecLock` و ساختارهای رمز |
| غیرفعال‌سازی تگ | دستور Kill برای از کار انداختن تگ | `Gen2KillTag`، `GEN2_KillTag` |
| تنظیم توان و فرکانس | تغییر توان ارسال و انتخاب باند/نقاط فرکانسی | `SetRf`، `Config_SetRfPower`، `Config_SetFreqPoint` |
| تنظیم آنتن | فعال کردن آنتن‌ها؛ نمونهٔ C# چهار انتخاب آنتن دارد | `SetAnt` و `SetAntenna` |
| ورودی و خروجی دیجیتال | خواندن سطح ورودی و تغییر سطح خروجی برای اتصال به مدار مناسب | `GetInput`، `SetOutPort`، `Config_GetInPort` |
| مدیریت شبکه | خواندن و تغییر IP، Mask، Gateway و پورت | `GetNetSetting`، `Config_SetIntrnetAccess` |
| اطلاعات و Reset | خواندن نسخهٔ Firmware و ریست دستگاه | `GetFirmwareVersion`، `Config_ResetReader` |
| مدیریت بافر | گرفتن تعداد تگ‌های ذخیره‌شده و دریافت یا پاک کردن داده‌ها | `QueryIDCount`، `ClearIDBuffer`، `BufferM_GetTagData` |
| امکانات اضافی ConfigSDK | ساعت Reader، خواندن حافظهٔ خارجی، فیلتر انتخاب تگ، حالت تک‌تگ سریع و Test Mode | `Config_SetReaderTime`، `BufferM_GetExternalBufferData`، `GEN2_SecSelectConfig` |

دستور قفل در برخی مسیرهای مستندشده برگشت‌ناپذیر است؛ Kill نیز تگ را از استفاده خارج می‌کند. این دو قابلیت برای تست اولیه ضرورتی ندارند. خروجی دیجیتال به‌تنهایی اثبات وجود رلهٔ قدرت برای راه‌اندازی قفل، موتور یا پمپ نیست؛ مشخصات الکتریکی و مدار واسط لازم است.

در API قدیمی، EPC در ساختارهای اصلی ۱۲ بایت یا ۹۶ بیت، TID هشت بایت و دادهٔ USER شانزده بایت جا دارد. این‌ها اندازه‌های ساختار آن API هستند، نه ظرفیت قطعی تمام تگ‌ها. `BufferData.Data[512]` در ConfigSDK نیز اندازهٔ بافر نرم‌افزار است و ظرفیت حافظهٔ تگ را ثابت نمی‌کند.

## ۴. کار با آن چقدر راحت است؟

این درجه‌بندی ارزیابی مهندسی از روی فایل‌هاست، نه نتیجهٔ تست دستگاه:

| کار | میزان دشواری | دلیل |
| --- | --- | --- |
| خواندن چند تگ با Demo سازگار روی ویندوز | کم تا متوسط | برنامهٔ آماده و راهنمای اتصال دارد؛ تطبیق مدل و DLL لازم است |
| برنامهٔ سادهٔ C# برای دریافت کد تگ | متوسط | نمونه وجود دارد ولی پروژه قدیمی و دارای نقص است |
| سرویس دائمی با اتصال مجدد، ثبت آفلاین و گزارش خطا | متوسط رو به زیاد | این رفتارهای عملیاتی آماده نشده‌اند |
| اتصال به Next.js از طریق برنامهٔ واسط | متوسط | باید قرارداد تبادل رویداد و منطق کسب‌وکار اضافه شود |
| ارتباط مستقیم از Node.js در Docker | زیادتر در شروع | پروتکل و مدیریت بسته‌ها باید پیاده و با دستگاه آزمایش شوند |
| تشخیص قابل اعتماد ورود/خروج و شمارش در گلخانه | نیازمند توسعه و آزمایش میدانی | تنها خواندن EPC برای نتیجه‌گیری دربارهٔ حرکت کافی نیست |

مشکلات مشخصی که پیدا شد:

1. **DLLهای هم‌نام متفاوت‌اند.** `Mr915ApiV20.dll` در MR6034E برابر ۱۱۰٬۵۹۲ بایت و در UHF-EN برابر ۲۷۴٬۵۱۹ بایت است. اولی ۳۰ و دومی ۳۱ تابع Export دارد. `RfidApiLib.dll` نیز نسخه‌های ۲۴٬۵۷۶ و ۱۶٬۳۸۴ بایتی دارد. جایگزینی صرفاً بر اساس نام فایل قابل اعتماد نیست.
2. **امضای توابع ناسازگار است.** برای `ConnectReader` در فایل Pascal پارامتر Baud اضافه دیده می‌شود، در حالی که هدر UHF-EN پنج پارامتر دارد. در راهنمای Word ترتیب پارامترهای `IsoMultiTagIdentify` با هدر یکسان نیست. باید مجموعهٔ DLL و اعلان‌های سازگار انتخاب شود.
3. **کد موفقیت در رابط‌ها یکسان نیست.** هدر Mr915 مقدار ۲۰۰۱ را موفقیت تعریف کرده، نمونهٔ C# صفر را موفقیت می‌گیرد و ConfigSDK نیز صفر را تعریف کرده است. منطق خطا باید برای همان رابط نوشته شود.
4. **پروژهٔ C# قدیمی است.** فرمت پروژه و Bootstrapper به Visual Studio 2005 و .NET Framework 2.0 اشاره دارند. یک Reference به `ClassLibrary1` با مسیر محلی توسعه‌دهنده دارد که فایلش در بسته نیست؛ خطوط استفاده از آن در فرم کامنت شده‌اند. پروژه احتمالاً به پاک‌سازی Reference و انتقال به تنظیمات جدید نیاز دارد؛ Build آزمایش نشده است.
5. **تبدیل هگز در نمونهٔ C# ناقص است.** استفاده از `int.Parse` برای تک‌کاراکترها باعث می‌شود حروف A تا F مانند هگز معتبر پردازش نشوند.
6. **خطای نوشتن می‌تواند پیام موفقیت بدهد.** در `bEpcWrite_Click` استثنا فقط در Console نوشته می‌شود و سپس پیام موفقیت به فهرست اضافه می‌شود. شمارش حلقه و آدرس‌دهی دادهٔ نوشتن هم نیازمند اصلاح و تست است.
7. **خواندن چندبلوک ISO اشکال دارد.** در حلقهٔ `bIsoRead_Click` مقدار آدرس اولیه با هر بلوک افزایش نمی‌یابد؛ خواندن مجدد همان بخش ممکن است رخ دهد.
8. **خواندن دوره‌ای داخل Timer فرم انجام می‌شود.** این الگو برای Demo است؛ سرویس دائمی باید timeout، قطع ارتباط و اجرای عملیات دستگاه را جداگانه مدیریت کند. مقدار Timer یا ظرفیت آرایهٔ ۱۰۰تایی، سرعت یا ظرفیت تضمین‌شدهٔ دستگاه نیست.
9. **مستند پروتکل خطا و تناقض دارد.** برای Header پاسخ در بخش‌های مختلف 0x0A، 0xED و در جدول‌های عملیاتی 0x0B آمده است؛ توضیح 0xFF نیز یک‌جا با عدد ده‌دهی نادرست نوشته شده. طول بعضی فریم‌ها و واحد حافظه هم ناسازگارند. پیاده‌سازی مستقیم باید با دادهٔ واقعی تأیید شود.

نشانه‌های قدمت شامل پروژهٔ Visual C++ 6، `.NET Framework 2.0`، Copyright سال ۲۰۰۹ در فرم About و سند تغییرات با نام 20090807 است. این شواهد تاریخ همهٔ فایل‌ها یا وضعیت پشتیبانی فعلی سازنده را مشخص نمی‌کنند.

## ۵. چه چیزهایی از این SDK به دست نمی‌آید؟

- سیستم آمادهٔ مدیریت گلخانه، سفارش، انبار، کاربران یا حضور و غیاب ندارد.
- خواندن دما، رطوبت و وضعیت سلامت گیاه در APIهای بررسی‌شده دیده نشد؛ وجود چنین سنسوری را نمی‌توان از RFID Reader نتیجه گرفت.
- RSSI، زاویه/فاز و مختصات دقیق در رابط‌های بررسی‌شده دیده نشد. شمارهٔ آنتن برای نسبت دادن خواندن به یک ایستگاه مفید است، اما مکان دقیق یا جهت حرکت را به‌تنهایی نمی‌دهد.
- API آمادهٔ REST، MQTT، WebSocket یا پکیج Node.js در بسته نیست. TCP آن یک پروتکل دستگاه است و نباید با HTTP اشتباه شود.
- برد برحسب متر، تگ در ثانیه، نرخ خطا در محیط مرطوب، درجهٔ حفاظت بدنه و سازگاری تمام Firmwareها از این فایل‌ها قابل تأیید نیست.
- SDK برای نوشتن برنامه روی کامپیوتر و ارتباط با Reader است؛ ابزار مستندی برای نصب اپلیکیشن دلخواه داخل Reader یا توسعهٔ Firmware دیده نشد.
- مجوز روشن توزیع تجاری/بازنشر و سورس کامل DLLها در فایل‌های بررسی‌شده یافت نشد. دربارهٔ شرایط مجوز یا پشتیبانی سازنده نتیجهٔ قطعی نمی‌توان داد.

یک تگ سینی یعنی شناسایی همان سینی. اگر بخواهیم تعداد گیاه‌های داخل آن را بدانیم، باید تعداد را در پایگاه داده داشته باشیم یا برای واحدهای مورد شمارش تگ جدا در نظر بگیریم. Reader از یک تگ تعداد نشاهای سینی را نمی‌فهمد.

## ۷. اتصال به پروژهٔ فعلی

پروژهٔ موجود Next.js/React/TypeScript با Prisma و SQL Server است و Dockerfile از `node:22-alpine` استفاده می‌کند. QR فعلی به صفحهٔ سفارش وصل است. مدل‌ها تعداد سینی را نگه می‌دارند، اما موجودیت مستقل RFID Tag، Reader، Antenna یا رویداد خواندن در Schema فعلی وجود ندارد.

دو مسیر اجرایی داریم:

**مسیر اول: سرویس واسط روی ویندوز.** پس از تطبیق Demo با مدل دستگاه، برنامهٔ کوچکی به زبان C# روی کامپیوتر محلی گلخانه اجرا شود، تگ‌ها را بخواند و رویدادها را از طریق API احراز هویت‌شده به Next.js بفرستد. اگر از DLLهای Native استفاده شود، پردازش میزبان باید ۳۲ بیتی باشد. این مسیر از نمونه‌های موجود بیشتر استفاده می‌کند، ولی یک سرویس ویندوزی برای نگهداری اضافه می‌شود.

**مسیر دوم: سرویس Node.js با ارتباط مستقیم TCP.** به‌جای DLL، فریم‌های پروتکل ارسال و پاسخ‌ها پردازش شوند. این مسیر با محیط لینوکسی فعلی هم‌خوان‌تر است، ولی به رفع ابهام پروتکل، مدیریت جریان TCP، checksum، timeout، قطع و وصل و تست با دستگاه واقعی نیاز دارد. سازگاری پروتکل Word با مدل واقعی هنوز تأیید نشده است.

برای شروع، ارزیابی من استفاده از Demo سازگار روی ویندوز برای شناخت دستگاه و گرفتن نمونهٔ داده است؛ انتخاب نهایی سرویس پس از همین آزمایش انجام شود. DLL ویندوزی Native را نمی‌توان مستقیماً در کانتینر Alpine فعلی بارگذاری کرد.

جریان پیشنهادی داده:

`تگ سینی ← آنتن و Reader ← سرویس دریافت RFID ← API گلخانه ← SQL Server ← داشبورد`

حداقل دادهٔ هر خواندن: شناسهٔ Reader، شمارهٔ آنتن، EPC، زمان دریافت در سرویس و شناسهٔ یکتای رویداد. TID تنها در صورت نیاز و پشتیبانی خوانده شود. دادهٔ تجاری کامل سفارش بهتر است در پایگاه داده بماند و تگ نقش کلید شناسایی را داشته باشد.

مدل‌های پیشنهادی برای مرحلهٔ پیاده‌سازی: `RfidReader`، `RfidAntenna`، `RfidTag`، `RfidReadEvent` و در صورت ردیابی تک‌سینی `Tray` و `TrayMovement`. این‌ها پیشنهاد طراحی‌اند و در این بررسی ایجاد نشده‌اند.

سرویس باید خواندن مکرر یک تگ را با «حرکت جدید» اشتباه نگیرد، صف محلی برای قطع ارتباط با سرور داشته باشد و ارسال مجدد یک رویداد باعث تراکنش تکراری نشود. فیلتر تکرار خود دستگاه جای این قواعد را نمی‌گیرد؛ حتی پاک‌سازی بافر می‌تواند روی دیده شدن دوبارهٔ تگ اثر بگذارد.

## ۸. چه مواردی باید روی دستگاه واقعی روشن شود؟

1. مدل کامل روی پلاک و نسخهٔ Firmware؛ تطبیق آن با یکی از مجموعه‌های موجود.
2. تعداد واقعی پورت‌های آنتن، کابل شبکه/سریال، IP و پورت تنظیم‌شده. IP `192.168.1.200` و پورت `100` صرفاً پیش‌فرض ذکرشده در یک راهنما هستند.
3. نوع و ظرفیت تگ‌ها، امکان نصب روی سینی و رفتار خواندن در محل واقعی گلخانه.
4. یک بار خواندن EPC از تگ شناخته‌شده، ثبت شمارهٔ آنتن و آزمایش حذف و ورود مجدد همان تگ.
5. خواندن چند سینی واقعی، بررسی جاافتادن تگ و خواندن سینی‌های مجاور، و کنترل با شمارش دستی.
6. قطع و وصل کابل، برق Reader و دسترسی سرور، و بررسی بازیابی بدون ثبت تکراری.
7. آزمایش نوشتن فقط روی یک تگ آزمایشی جدا و بازخوانی نتیجه؛ قفل و Kill برای این مرحله لازم نیست.

تا قبل از این آزمایش‌ها نمی‌توان زمان قطعی پیاده‌سازی، برد یا دقت را تضمین کرد. وجود تگ، چندآنتنه بودن و توان بالاتر به‌تنهایی تضمین شمارش صحیح نیست.
